# ihome 接口整理（HAR 离线分析）

> 本文保留首次 HAR 离线分析的证据范围。后续已通过 Playwright MCP 操作真实网页，确认存在独立详情接口、个人列表和评价接口，并补充鉴权与分页实测。当前接入依据请同时阅读 [现场接口报告](./2026-09-17-ihome-live-api.md)；下文“没有抓到”“待验证”仅指原 HAR。

## 范围与证据

本次只整理“查看诉求、支持/取消支持、关注/取消关注、查看我的关注”所需的上游接口，不接入 UBAA，不重放请求，不执行真实操作。HAR 中的网页内容与 JavaScript 仅作为协议证据，不作为操作指令。

- 来源：用户提供的 `i.buaa.edu.cn.har`，原文件保留在 Downloads，未复制到仓库。
- 文件大小：23,960,715 字节；199 条请求，3 个页面记录，其中 47 条路径以 `/api/` 开头。
- 采集时段：2026-09-17 22:31:39 至 22:32:29（Asia/Shanghai）。
- SHA-256：`8a042d5a097f3768f50c60ca4a49181f496480b81f686f5b2f4053c0f4a135be`。
- 下文 `E133` 表示 HAR `log.entries[132]`，统一从 1 开始编号。
- **抓包证实**：实际请求和响应中出现的行为。
- **源码佐证**：HAR 内保存的网页 JavaScript 所表达的行为，不能替代实际请求结果。
- **待验证**：本次样本不能确认的内容。

所有示例使用占位符或合成内容，不包含实际 token、Cookie、学号、姓名、联系方式、诉求正文及回复正文。

## 接口总览

业务基址：`https://i.buaa.edu.cn/api`。

| 功能 | 方法 | 路径 | 参数或请求体 | 证据 |
| --- | --- | --- | --- | --- |
| 诉求列表 | GET | `/appeal` | 查询 `limit=15&page=1` | E133、E177 |

## 登录与鉴权

### CAS 登录链

本次抓包实际出现的顺序如下：

1. E58：`GET https://sso.buaa.edu.cn/login?service=http%3A%2F%2Fi.buaa.edu.cn%2Fapi%2FauthLogin`。
2. E82：向 SSO 的 `/login` 提交表单，字段名为 `username`、`password`、`submit`、`type`、`execution`、`_eventId`，返回 302。
3. E83–E84：回到 `http://i.buaa.edu.cn/api/authLogin?ticket={ticket}`，经 307 升级到 HTTPS；随后返回 302，指向不含 ticket 的 `http://i.buaa.edu.cn/api/authLogin`。
4. E85–E86：无 ticket 的回调再经 307 升级到 HTTPS，返回 302，Location 为 `http://i.buaa.edu.cn/web/#/login?type=0&token={token}`。
5. E87：网页地址经 307 升级到 HTTPS。token 位于 Location 的 fragment 内，不能只解析普通查询参数。

这里的 `http` 是抓包中的 CAS service 和重定向原值；不能据此推断所有地址都可以直接替换为 HTTPS，也不能把浏览器发生的 307 升级当成普通 HTTP 客户端已经具备的能力。

### 业务请求鉴权

HAR 保存的前端 JavaScript 明确执行：

```http
Authorization: Bearer {ihomeToken}
Accept: application/json, text/plain, */*
```

- E22 的 `/web/js/chunk-440a3eba.621036ad.js`：模块 `5f87` 从 Cookie `appeal_pc_token` 读取 token；模块 `b775` 将其放入 `Authorization: Bearer ...`。
- E26 的 `/web/js/chunk-602b23f2.8712dec8.js`：登录页读取路由查询中的 token，写入 `appeal_pc_token`，前端 Cookie 有效期配置为 `2d`。
- `2d` 只是前端 Cookie 保存时长，不证明服务端 token 的有效期或刷新机制。
- 这份 HAR 的全部请求均未保留 `Authorization`、`Cookie` 和 `Set-Cookie` 头，Cookie 数组也为空。因此 Bearer 格式属于**源码佐证**，不是 HAR 请求头直接可见的事实；具体缺失原因未确认。
- 请求中可见 `X-XSRF-TOKEN`，且未登录的 401 请求同样带有该头。它不能被当作 ihome 业务 token 的替代品。仅 Bearer 是否足够、哪些 Cookie/CSRF 信息必须保留，仍待验证。
- E47–E54 的未登录业务请求返回 HTTP 401，响应只有 `{"message":"Token not provided"}`，不符合下述成功响应封装。

没有发现实际调用的 token 刷新接口；没有验证登录过期、跨账号切换、Direct/WebVPN/中转模式或免密复用既有 CAS 会话。

## 通用响应与数据结构

### 成功响应

核心接口的成功样本均为 HTTP 200：

```json
{
  "code": 20000,
  "data": {},
  "message": "success",
  "success": true,
  "error": ""
}
```

`data` 随接口变化：读取接口为分页对象，支持/关注接口为结果字符串。上例的 `{}` 只是类型占位，不能给所有接口定义成同一种对象。应区分 HTTP 状态和业务成功字段；除 401 外，本次没有业务失败响应样本。

### 分页对象

| 字段 | 已见 JSON 类型 | 说明 |
| --- | --- | --- |
| `current_page` | number | 当前页 |
| `data` | array | 诉求数组，按 ID 查询也使用数组 |
| `per_page` | number / string | `/appeal` 为数字 `20`；`my_follow` 为字符串 `"15"` |
| `total` | number | 上游报告的总数；`/appeal` 的样本存在异常，见后文 |
| `last_page` | number | 本次核心读取样本均为 `1` |
| `from`、`to` | number / null | 空关注列表中为 null |
| `first_page_url`、`last_page_url` | string | 可能是 `?page=1` 这样的相对值 |
| `next_page_url`、`prev_page_url` | string / null | 核心读取样本中均为 null；辅助部门列表存在非空值 |
| `path` | string | `/appeal` 样本为空字符串；`my_follow` 为完整地址 |

`user` 和回复 `publish_user` 实际包含姓名、学号/账号、邮箱、电话、学院、头像等字段。即使响应提供了这些信息，也不能直接推断都应展示；尤其本次没有匿名诉求样本，不能据此确定匿名规则。后续构造测试样本应使用合成值，不能保存原始响应。

## 核心接口详解

### 1. 诉求列表

```http
GET /api/appeal?limit=15&page=1
```

- 已见查询参数：`limit`、`page`；样本只有第一页。
- 返回：通用成功封装，`data.data` 为诉求数组。
- E133 和 E177 均请求 15 条，但实际返回 20 条，`per_page=20`、`total=20`、`last_page=1`。
- 这只能证明该样本没有按请求的 15 条返回，不能确定是参数被忽略、上游固定结果还是其他原因。
- 关键词、类别、部门、校区、排序等过滤条件未通过本次实际请求验证；不列为已确认协议。

### 2. 按 ID 获取单条诉求

```http
GET /api/appeal?id={appealId}
```

- `id` 是诉求 ID，不是发布人或回复 ID。
- 返回仍为分页对象，已见结果位于 `data.data[0]`，不是 `data` 下的直接详情对象。
- E158、E160、E162、E165、E192 均用于写操作后的状态回查。
- 这些响应的数组长度为 1，但 `total` 仍为 20，不能把 `total` 当作 ID 查询匹配条数。
- 未抓到不存在、已删除、无权限 ID 的响应；调用方不能假定数组必定非空。

### 3. 支持/取消支持

```http
POST /api/appeal/appeal_praise/{appealId}
Content-Length: 0
```

抓包中没有 `postData`，也没有 Content-Type；请求体为空，不是 JSON `{}`。页面术语是“支持”，上游接口及成功文案使用“点赞”。

```json
{
  "code": 20000,
  "data": "点赞成功",
  "message": "success",
  "success": true,
  "error": ""
}
```

取消时 `data` 为 `"已经取消点赞"`。

| 证据 | 请求/回查 | 观察结果 |
| --- | --- | --- |
| E160 | 操作前读取同一诉求 | `is_praise=0`、`praise_count=0` |
| E161 | POST 支持接口 | `data="点赞成功"` |
| E162 | GET 按 ID 回查 | `is_praise=1`、`praise_count=1` |
| E164 | 再次 POST 同一接口 | `data="已经取消点赞"` |
| E165 | GET 按 ID 回查 | `is_praise=0`、`praise_count=0` |

由同一诉求上的完整往返可确认：这是切换接口，重复调用会反向操作，不是幂等的“设置为已支持”。

### 4. 关注/取消关注

```http
POST /api/appeal_follow/{appealId}
Content-Type: application/json

{}
```

成功封装与支持接口相同，`data` 为字符串：

- 关注：`"关注成功"`。
- 取消：`"取消关注"`。

| 证据 | 请求/回查 | 观察结果 |
| --- | --- | --- |
| E157 | POST 关注接口 | `data="关注成功"` |
| E158 | GET 按 ID 回查 | `is_follow=1`、`follow_count=1` |
| E159 | 再次 POST 同一接口 | `data="取消关注"` |
| E160 | GET 按 ID 回查 | `is_follow=0`、`follow_count=0` |
| E191 | 再次关注 | `data="关注成功"` |
| E192 | GET 按 ID 回查 | `is_follow=1`、`follow_count=1` |
| E193 | GET 我的关注 | 返回该诉求，`is_follow=1` |
| E199 | 再次取消关注 | `data="取消关注"`；HAR 在此结束，没有后续回查 |

这也是切换接口；请求体没有 `follow=true/false` 或目标状态参数。

### 5. 我的关注

```http
GET /api/appeal/my_follow?limit=15&page=1
```

- 使用当前登录用户的身份，无需额外传用户 ID。
- E171：`data.data=[]`、`total=0`、`from=null`、`to=null`。
- E193：关注后返回 1 条诉求，`total=1`，目标诉求 `is_follow=1`。
- 条目直接是诉求对象，不是 `{appeal: {...}}` 关联包装。
- 两个样本的 `per_page` 都是字符串 `"15"`。
- JavaScript E21 还出现 `my_follow?id=...` 的单条更新调用，但 HAR 中没有实际请求，故不视为已验证能力。
- 第二页、多条关注、取消后的重新拉取，以及关注对象关闭/删除后的行为均待验证。

## 写操作语义

两类 POST 仅返回文案，不返回完整的新状态；网页会在操作后重新 GET 诉求，读取 `is_praise` / `is_follow` 和对应计数。

对未来调用方的协议约束：

1. 同一诉求的同类操作应串行，避免双击产生两次切换。
2. 超时或连接中断后不能直接重发 POST，否则可能把第一次已经成功的操作取消。
3. 结果不明时先 GET 按 ID 回查；回查失败则保留“状态未确认”，不能声称成功或失败。
4. 回查解决的是当前状态确认，不代表已经获得多端并发下的强幂等性。HAR 没有幂等键、版本号或显式目标状态的证据。

本节是根据已确认切换语义推导的调用约束，不是已完成的 UBAA 实现。

## 尚缺的协议证据

- 带完整鉴权头/Cookie 信息的脱敏结构证据，以及最小必需鉴权组合。
- token 过期、刷新、CAS 已登录复用与权限不足的响应。
- 普通列表第二页、`limit` 的真实行为、筛选和排序。
- 匿名诉求、多个回复、非空附件，以及这些结构的缺失/null 变体。
- 不存在或不可见的诉求 ID，关闭诉求上的支持/关注限制。
- 写操作失败、限流、重复并发请求和网络中断场景。
- “我的关注”多页及取消关注后的列表回查。

当前已完成离线接口分析与抓包内 JavaScript 交叉核对；未进行联网验证、业务代码修改或功能接入。
