# UC 与 BYXT 登录链排查（2026-10-21）

后续补充：用户提供希冀 HAR 后，在 v1.8.2 清洁会话中复现了希冀返回空列表的问题，涉及希冀独立 CAS service、历史课程排除和 WebVPN 课程会话竞争。本文 UC/BYXT 验证不覆盖希冀验收；原 5 项固定日期测试已在后续修复中改用固定测试时钟。详见[希冀排查与验证记录](2026-10-21-judge-login-har.md)。

## 范围与证据

- 分析用户提供的 `uc.buaa.edu.cn.har`（131 个请求）和 `byxt.buaa.edu.cn.har`（90 个请求）。下文请求编号从 0 开始。
- 两份 HAR 都是成功登录样本，均未包含 Cookie/Set-Cookie；不能据此还原具体 Cookie 值或属性。
- 原始 HAR、账号密码、execution、ticket、用户资料和浏览器指纹不写入仓库。网页中的指令性文本仅视作附件数据。
- 当前项目为 Kotlin Multiplatform/Compose，排查基线为 `dev` 分支 `e8a397fc`。按用户确认，修复范围仅包含直连和 WebVPN；服务器中转已弃用。

## 登录链对比

| 阶段 | UC HAR | BYXT HAR | 项目实现与结论 |
| --- | --- | --- | --- |
| 获取登录页 | #1：SSO `/login`，不带 service | #3：SSO `/login?service=教务入口` | App 先建立通用 SSO，再分别激活 UC 和业务系统，顺序本身合理 |
| 浏览器指纹 | #23：POST `/fingerprint` | #25：POST `/fingerprint` | App 未执行该脚本；脚本即使上传失败或超过 500ms 也会执行原登录函数，不能仅因缺少此请求就认定为根因 |
| 提交凭据 | #24：POST `/login` → 302 | #26：POST `/login` → 302 | 两份表单均为 username、password、submit、type、execution、_eventId；项目普通密码登录的字段与之匹配 |
| 建立业务会话 | #71：UC status 为 10600；#72–76 再进行 UC → SSO → UC 票据交换 | #27：带 ticket 返回教务；#28：去掉 ticket 后加载页面 | SSO 提交成功不等于 UC 已登录，也不等于教务已登录 |
| 协议升级 | #72 Location 为 HTTP SSO；#74 实际访问 HTTPS SSO | #0 Location 为 HTTP BYXT；#1 浏览器以 `HttpsUpgrades` 307 改为 HTTPS | 浏览器会做的协议升级，原生 HTTP 客户端不能默认继承 |
| 验证成功 | #125/#129：UC status code=0；#130：userinfo code=0 | #38/#49：门户 currentUser code=0，用户对象在 datas 下 | App 主登录以 UC status 为准；教务会话由 currentUser 探测，不能用门户 HTML 的 HTTP 200 代替 |

BYXT 的 `/jwapp/sys/byrhmhsy/index.do` 是本次样本中的混合门户入口，随后通过页面脚本进入门户，再访问 `/jwapp/sys/homeapp/index.do`。App 当前直接探测 HTTPS `/jwapp/sys/homeapp/api/home/currentUser.do`，不访问根目录，因此不需要复制首页的脚本导航或 HTTP 根目录跳转。

## 确认的问题及修复

`LocalAuthServiceBackend.activateUcLogin()` 原先只调用自动跟随重定向的客户端。UC `/api/login` 返回指向 HTTP SSO 的 Location 时，Ktor 默认不跟随 HTTPS → HTTP 降级；随后调用 UC status，得到未登录，最终被呈现为登录失败。无凭据的实时 GET 也确认了该 HTTP Location 仍在返回。

修复后的激活流程使用不自动跳转的客户端，复用登录跳转处理：

1. 解析 Location；WebVPN 地址先还原为上游地址。
2. 仅将 `sso.buaa.edu.cn` 默认 HTTP 端口升级至 HTTPS，原样保留 service 等嵌套查询编码，不改写其他业务系统的 CAS service。
3. WebVPN 模式重新包装地址，所有主登录跳转维持网关路由。
4. 跟随 UC ticket 回调，保存 Cookie，再以 UC status 判断登录结果。
5. 超过 10 次跳转时终止，防止循环。

WebVPN 登录后的辅助直连 SSO 会话明确使用直连路由，并完成 UC 激活链，避免受当前 WebVPN 模式影响。

新增的完整票据交换回归测试在修复前失败、修复后通过。覆盖直连/WebVPN、预登录/密码登录、网关包装与原始 HTTP Location、Cookie 传递、循环终止及 service 编码保护，测试值均为合成数据。

## 中转模式弃用

App 首次选择、登录页切换和设置页共用的可选模式现在只有直连、WebVPN。旧中转配置在启动时清除会话并关闭自动登录，返回选择页；已记住的账号密码保留。初始化认证时同步表单中的自动登录状态，避免迁移后启动页仍等待旧状态。Web/Wasm 无法进行本地连接，显示使用原生客户端的提示，不再自动选中中转。服务端与旧 relay 实现保留兼容代码，本次不再修复其登录流程。

## 实际验证

使用本机测试凭据及项目 JVM 登录实现，所有 Settings、Cookie、会话均放在内存中，关闭 HTTP 原文日志及登录统计上报：

- 直连：UC status 验证成功且账号匹配；BYXT 会话探测为 `UNDERGRAD_READY`。
- WebVPN：UC status 验证成功且账号匹配；BYXT 会话探测为 `UNDERGRAD_READY`；辅助直连认证也完成。
- 两条路径均未发送 `/fingerprint`。这证明当前测试账号在此次环境下不依赖指纹请求，不能推广为学校未来所有风控场景都无需指纹。
- 直连 UC 首页曾返回 404；WebVPN 初始导航曾经过 `/wengine-vpn/failed`，随后显式 UC 激活仍成功。验收依据是最终 UC status 和教务会话探测，而非中间落地页。
- 这是 JVM 协议层实测，不代表 Android/iOS 真机界面验收，也未提交选课、签到或其他业务写操作。
- 最终定向检查：shared 的登录、连接模式、WebVPN 与 API 分发测试 29 项通过；Compose 全量测试 165 项通过。共享代码的 Android、iOS Simulator ARM64、JS、Wasm 编译通过，文档构建和 Spotless 检查通过。
- shared 全量测试运行 223 项：205 项通过、13 项跳过、5 项失败。失败均来自 `LocalJudgeApiBackendTest` 的固定日期样例；将本次改动的认证和连接模式生产文件还原到基线后，这 5 项仍同样失败。样例开始日期为 2026-04-20，当前已被六个月历史筛选规则过滤，与本次登录修复无关。
