# 本地错误定位与诊断

本手册供处理用户报错的维护者和新增错误场景的开发者使用，说明用户如何提供诊断信息、维护者如何据此定位问题，以及诊断功能的开发规则。

## 何时使用

- 用户报告登录、读取或提交失败，并提供了错误编号或诊断报告。
- 需要判断失败发生在哪一层（UI、应用层、Bridge、Core 或网络传输）。
- 新增或修改错误场景、诊断字段。

## 前提

用户获取诊断信息的方式：

- 在错误卡、行内提示或写入提示打开“错误详情”，选择“分享报告文件”或“保存报告文件”。报告对应当前错误和关联记录。记录过期后仍可复制或导出当前错误的安全摘要，`record_available=false` 表示历史记录已不可用。
- 登录页和启动失败页通过“查看诊断信息”打开报告。进入主页后，在“我的 → 诊断信息”查看当前及历史记录。
- Android、iOS、HarmonyOS 和 macOS 打开系统分享面板。Windows 和 Linux 提供“保存报告文件”。打开分享面板或保存到本机不会发送报告。选择“前往反馈”可打开项目的 [GitHub Issues](https://github.com/BUAASubnet/UBAA/issues)，用户自行创建 Issue 并附上检查过的报告。

诊断的边界：

- 分享和保存均由用户主动操作。完整报告不会自动上传。界面不展示或复制报告内容；错误现场只显示错误编号和代码，并指引到“设置 › 诊断信息”分享完整诊断。登录页和启动失败页无法进入设置，直接提供“诊断信息”入口。
- 分享附件使用 UTF-8 JSON，文件名为 `UBAA-report-<时间戳>.json`。系统缓存中的分享附件在后续分享时清理七天前的文件，已交付给接收方的文件由接收方管理。
- 报告保留本次运行及此前七天内最近 100 项错误。宿主将安全字段保存到本机偏好存储，重启后通过 `previous_events` 导出历史记录。启动失败记录能取得的平台和应用版本（含构建号），并以 `initialization_stage` 区分 SDK、Bridge 校验、平台能力、后端打开、应用装配和会话恢复阶段。
- 普通摘要不读取凭据或会话文件，不保存原始 HTTP 数据。设置中的“分享完整诊断”（桌面为“保存完整诊断”）在用户操作时附加当前客户端的原始响应，不做字段脱敏。
- 普通摘要使用 `schema_version=3`，完整诊断使用 `schema_version=4` 和 `report_type=full_diagnostics`，与 CLI 和 Bridge 合同版本无关。

## 完整诊断

设置中的“诊断信息”只提供“分享完整诊断”（桌面为“保存完整诊断”），并明确提示不得公开分享。导出时额外附加 `raw_http`，包含学校请求方法、完整地址、实际路线、请求编号、开始时间、耗时、响应状态、重复响应头及完整正文。文本以 UTF-8 保存，其他字节以 Base64 无损保存。记录包括成功响应、重定向、认证和内部重试，通过编号与时间顺序查看。错误摘要包含保留范围内的全部事件，按错误编号查找关联记录。

原始响应可能包含个人数据、Cookie 和业务 Token，只私下发送给可信任的维护者，不发到群聊、论坛或 GitHub Issues 等公开场所。该信息不自动上传，不保存到偏好存储。原始缓冲只在当前客户端生命周期有效，路线切换与派生读取共享记录；重建客户端或重启后需要重新复现。普通错误历史仍可保留七天。

缓冲最多保存 256 条、32 MiB 序列化记录，按完整记录淘汰，不截断正文。超过容量的单条记录不保留，`dropped_records` 统计全部淘汰与超限记录。`started_requests`、`completed_requests` 和 `unfinished_requests` 区分已开始、已完成以及尚未完成或被取消的请求。流式下载文件不复制进报告，`body_capture=delivered_to_file` 明确标记；传输未能返回响应时只有 `transport_error`，不能补回未接收的字节。传输原有响应体预算仍然有效。

## 步骤

1. 用错误编号关联本次运行的报告，查看 `operation`、`code`、`kind`、`route`、`feature`、`cause` 和 `source`。需要定位提交时查看 `write_operation`；云打印批量报告用 `file_index` 表示从 1 开始的文件序号，不含文件名。
2. `source` 只含允许的 UBAA package 源码位置，去重后最多八项，不含本机绝对路径或完整堆栈。没有安全源码位置时不猜测。
3. 按阶段定位代码：

   | 阶段 | 查看 |
   |---|---|
   | 初始化、登录、路线切换 | app/controller |
   | 读取 | 对应的 bridge/read 与 Core feature |
   | 写入准备、提交、丢弃 | WriteCoordinator |
   | 回读 | ReceiptVerifier 和对应的 controller/readback |

4. 查看 `diagnostic.source` 指向的 Rust 判定分支，并结合 `stage`、`reason`、HTTP 状态和响应结构定位。发送或接收失败的安全原因已进入报告；需要额外耗时日志时，再取得下文的 stderr 证据。

解读报告时：

- `retryable=false` 必须保留。`outcome_unknown` 始终先核对状态，不能用通用重试入口重复提交。
- 报告中的失败路线来自本次错误，不是默认策略或上次成功的快照。
- `business_rejected` 表示学校服务按已知格式拒绝业务操作；`parse_error` 表示响应无法解析；`upstream_changed` 表示响应结构与已验证格式不符。HTTP 403 只说明学校服务拒绝访问，HTTP 429 标记为 `http_rate_limited`。

## 操作上下文与关联记录

`requested_policy` 表示操作记录时的连接策略，`route` 表示错误携带的实际路线。请求发送前被本地拒绝时可以没有实际路线，不能用策略补成已经完成的选路。`latency_ms` 记录有计时入口的操作耗时，`recovery_attempts` 记录本次专用服务恢复流程的尝试次数。

专用服务恢复失败时，报告同时保留原始读取错误与最终错误，用 `related_issue_id` 关联。查询其中任意编号会导出完整关联链，包括重启后的记录；全量报告仍将历史事件放在 `previous_events`。恢复成功不追加错误事件，账号或网络代次变化后的过期任务不进入当前报告。

本地能力错误可携带 `local_reason`：权限类型和状态、凭据存储类别、安全材料事务是否结果不明、日程存储类别和日程文件保存失败。全部值由固定枚举生成，不使用系统异常正文。这些本地上下文字段不进入自动遥测。

| 功能范围 | 主要定位信息 |
| --- | --- |
| 认证、会话、账号与路线 | 认证阶段、会话修订冲突、共享身份撤销、网络变化及实际拒绝位置 |
| 课表、考试、成绩、空教室、每日课程 | 业务调用位置、JSON 类型与语法错误行列、业务状态及实际路线 |
| 博雅、图书馆、研讨室、体育、评教、SPOC、希冀 | 原有业务原因、HTTP/解析摘要、实际错误位置；Dart 映射保留原始异步调用栈 |
| 财务 | 门户、票据交换、查询登录、收入响应、字段与金额、分页分别记录；固定字段名进入原因码，字段值不导出 |
| 门户、iHome、云盘、云打印 | 读取或写入操作、恢复关联、传输及存储原因；专用操作记录耗时，批量失败保留文件序号 |
| 日程、缓存、应用服务、启动与平台能力 | 本地失败位置、缓存具体类别、初始化阶段和可取得的固定本地原因；SQLite 锁忙的 `cause` 为 `cacheBusy` |

字段校验的原因码可以包含固定字段名、预期类型和实际类型，例如 `rows_expected_array_got_string` 表示 `rows` 需要数组，实际返回字符串；`xnxqdm_expected_text_got_missing` 表示学期字段缺失。字段名来自源码常量，字段值不导出。

财务中 `je_type_invalid` 表示金额字段类型不符，`lsh_missing` 表示流水号缺失，`record_duplicate` 表示分页中出现重复记录。成绩读取前的待确认写操作报告 `write_confirmation_pending`；固定路线返回不符报告 `pinned_route_mismatch`。先依据应用版本找到对应源码，再查看诊断位置，不能把公共 helper 的名称当作最终根因。

## 已知边界

报告描述客户端观察到的失败条件。连接失败无法一律细分为 DNS 或 TLS 根因，服务器未公开的内部故障也不能从 HTTP 状态反推出。原生插件已经归约的异常只能报告已知能力、状态和本地调用点。历史报告中没有采集的上下文无法补回。

## Rust 传输补充证据

具体 HTTP 适配器的 `ubaa::transport` tracing 事件只包含固定阶段、保守的原因分类和耗时：

- 发送、响应读取和响应超出预算分别记录。
- 分类只依据稳定的 Reqwest 判断和最多八层标准 I/O 错误链，不格式化原始错误，不记录请求或响应数据。

两种宿主的输出方式：

- 生产 Bridge 初始化时安装一个 stderr 日志订阅器，只接收该安全 target 的 DEBUG 四字段事件；宿主已有全局订阅器时不覆盖。它不读取 `RUST_LOG` 放宽过滤，也不启用第三方详细日志。
- CLI 默认不输出这些事件，保持 JSON 命令的安静错误输出。排障时显式设置 `RUST_LOG=ubaa::transport=debug`。

Flutter 本地报告包含操作、源码位置以及随错误传递的传输阶段和原因。Rust stderr 额外提供传输耗时事件。本地报告不包含完整的 Rust 错误链，也不自动收集系统日志。

## 验证

- 定位结论应能对应到报告中的 `code`、`kind` 和 `source`，以及必要时的传输阶段分类。
- 本地诊断不改变业务结果。可选遥测异步执行且有两秒截止预算，异常只记录到本地，不会把登录、读取或提交改成失败。
- 过期读取和已销毁控制器的迟到结果不进入当前页面的诊断。

## 故障处理

- 无法确认 DNS/TLS 的具体原因时保留 `connect`/`unknown`，不要求用户关闭 TLS 进行验证。
- macOS 系统的 network-outbound 拒绝等平台证据可以作为独立排障输入；不在普通报告中粘贴整段系统日志或个人页面。
- 打包权限问题使用实际产物的 Sandbox/network.client 检查（`just flutter-artifact-check`），不能只看源码 entitlement。

## 开发规则

- UI 只使用 platform 的共享错误模板；app 的 `UbaaErrorMapper` 是兼容适配入口，不新增第二份策略。
- Bridge typed 错误使用穷尽枚举映射；兼容 JSON 只解析固定字段，未知路线归空。
- 不把外部错误的原始文本当作已脱敏内容保留。普通诊断只保留允许的字段；原始字符串只通过主动分享的完整诊断出口传递。
- 新错误场景先写从真实适配器或控制器到最终状态的失败测试，并检查原文只进入完整诊断，不进入普通 UI、日志、摘要存储或遥测。
- 检查按[检查选择与完成条件](../development/commands.md#检查选择与完成条件)执行，日志字段按[日志与诊断脱敏](../development/conventions.md#日志与诊断脱敏)处理。
- 全量门禁、宿主 integration、本地回环和真实学校验证的结果分别记录。真实 App 与 Core-live 按 [来源对照与真实验证](../development/commands.md#来源对照与真实验证)运行。

## 结构化错误上下文

`diagnostic` 保留 Rust 源码位置、失败阶段和原因。响应诊断包含 HTTP 状态、响应长度与类别、允许字段的 JSON 类型及解析行列。博雅业务拒绝可携带已确认无个人数据的固定上游提示，未知正文不自动共享。

允许统计时，读取和写入按操作结果计数，同时上报通过校验的诊断字段，界面展示不重复计数。完整报告和本地错误编号不上传。服务端 `error_samples` 与错误计数分开存储，每个安装、日期、版本和错误维度保留最新样本，14 天后清理，安装级删除同时删除样本。先部署识别新事件的服务端，再发布客户端。

在[维护者错误看板](app-service.md#使用情况看板)选择版本、功能、路线和错误码，查看失败次数以及样本中的源码、阶段、原因、HTTP 状态和业务码。也可在受限数据库会话中查询最近的样本：

```sql
SELECT day, app_version, feature, route, error_code,
       diagnostic->>'source' AS core_source,
       diagnostic->>'stage' AS stage,
       diagnostic->>'reason' AS reason,
       diagnostic->>'status' AS http_status,
       diagnostic->>'upstream_code' AS upstream_code
FROM error_samples
ORDER BY day DESC
LIMIT 20;
```

同一错误的计数仍从 `error_days` 或 `error_daily` 查询，样本条数不等于失败次数。
