# 应用服务实施计划

更新：2026-11-11。状态：工程实现完成。生产部署未执行，验收范围见[迁移状态](../../project/status.md#应用服务验收对照)。

目标：完成经用户同意的遥测、更新检查、公告与更新门控，交付可以本地完整验收、可以按明确配置部署的客户端和 Worker。

设计依据：[应用服务合同](../../contracts/app-service.md)、[ADR 0008](../../adr/0008-app-service-worker.md)。合同规定行为和数值，本计划规定实现顺序与验收方式。长期规则遵循 [AGENTS.md](../../../AGENTS.md)，当前入口为 [goal.md](../../project/goal.md)。

客户端由 Rust Core 持有安装级状态、SQLite 队列、独立 transport 和门控。Dart 负责白名单、交互和宿主生命周期，经 typed Bridge 使用 Core。TypeScript Worker 使用 D1 存统计数据、KV 存渠道配置与公告。工具版本沿用仓库锁定值，新依赖只为本任务所需能力引入并提交锁文件。

## 交付范围与执行方式

本计划是一个完整功能任务，步骤包含各自的实现、接线、失败反例、修复和复审。首个端到端样例只用于尽早验证边界，最终交付必须覆盖合同全部事件、接口、状态转换和第 13 节验收场景。

无人值守执行采用以下规则：

- 按步骤连续推进，不在提交、测试通过或复审结束后等待人工确认。文件拆分、测试组织和其他不改变合同的实现选择由执行者决定。
- 每个行为先建立可观察的失败反例，再实现最小变更。测试通过后进入下一步，只在新改动或新证据出现时扩大或重复检查。
- 接续执行时先核对工作树、最后提交和已完成步骤，再继续未完成工作。已通过检查的代码范围和环境未变时复用结果。
- 本地工程操作和提交按当前会话授权执行。远端推送、生产部署、发布和学校请求按项目授权规则处理，凭据存在不构成授权。
- 工具或依赖故障先定位并修复。临时网络失败可有限重试，重复出现同一错误后换用项目支持的解决办法，避免无限重试。
- 缺少外部条件时记录受影响的验收项并继续无依赖工作。必需检查仍有失败或未完成时，状态保持未完成；不能以忽略测试、放宽白名单或取消门禁结束任务。
- 实际结果写入迁移状态，验证摘要写入提交说明。临时材料和运行证据放在 `.ubaa_local/app_service/`，敏感材料按项目规则设置私有权限。

## 步骤二：实现 Core 共享状态和队列

产物：无真实服务依赖的同意、开关、账号登记、队列、冻结和删除状态机。

- [ ] 在 Core 建立安装级 SQLite 存储，复用项目数据库连接、事务和迁移约定。GUI 与命令模式使用同一配置目录和数据库位置；账号切换不能另建安装 ID 或同意状态。数据库升级失败不得清空用户已有业务数据。
- [ ] 先实现状态测试，再实现 `unasked`、`agreed`、`reconsent_required`、`basic` 转换。遥测开关独立持久化，只有首次同意且无保存值时初始化为开启，旧 Noop 下的偏好按 ADR 忽略。
- [ ] 统一判定服务可用性、同意状态、遥测开关、硬关闭和删除标记，规则按合同第 2 节：
  - 可用性只由构建期配置得到，包括服务地址、渠道、可解析的版本，以及“Release 构建”或“非 Release 构建且地址为本机回环”；
  - `UBAA_TELEMETRY=0` 和非空 `CI` 只能关闭遥测；
  - 不实现运行时的“测试环境”探测，也不增加任何能开启应用服务的环境变量；测试通过可注入 transport 构造客户端；
  - 分别测试地址或渠道缺失、版本为空或格式不符、非 Release 构建配置非回环地址、Release 构建配置 HTTP 地址、`UBAA_TELEMETRY=0` 和非空 `CI`，断言停用时没有任何请求。

  Dart 仅展示状态；Core 在入队、冻结和发送前检查共享状态，不能依赖进程启动时缓存的布尔值。
- [ ] 实现白名单计数及用户登记。账号只来自已确认绑定，按校园日期、版本和账号登记，每日最多三个不同账号。支持会话恢复、离线查看、跨午夜与同日升级，退出或切换账号后不继续使用旧绑定。
- [ ] 实现学号规范化、固定前缀 SHA-256 和年级解析，测试使用合成输入并只输出断言结果。未知格式按合同返回 `unknown`。
- [ ] 实现持久化批次：按旧日期优先取合法子集，至多八个日期版本组合，各数组至多 512 项，序列化正文不超过 120 KiB；余量留在待发区。冻结后的 ID 和正文保持不变。
- [ ] 实现包含重试批次的 256 KiB 总容量、未冻结数据七天过期、冻结批次全部过期才删除，以及关闭统计清空全部待发数据。
- [ ] 响应处理只更新或删除仍然存在的批次行，不重新插入，避免另一进程删除后旧批次复活。两个进程可以同时发送同一批次，客户端不加锁，由服务端去重。
- [ ] 使用同一 SQLite 文件的两个独立连接验证状态变化，再加入独立进程用例验证重启恢复。可注入时钟和请求屏障用于控制顺序，不依靠随机延时。

关键测试的输入与结果：

| 操作序列 | 必须观察到的结果 |
| --- | --- |
| 同意 → 关闭统计 → 政策升级 → 重新同意 | 保存的开关仍为关闭，队列为空，没有遥测请求。 |
| 已冻结批次收到 503 → 关闭 → 开启 | 原批次已删除，不会在重新开启后发送。 |
| 进程 A 缓存开启状态 → 进程 B 关闭 → A 入队 | 共享状态拒绝入队，数据库无新增。 |
| 进程 B 标记删除 → 两个进程重启 | 删除标记和旧安装 ID 仍在，冻结与上传均停用。 |
| 进程 A 发送批次期间进程 B 删除成功，A 随后收到 503 | 旧批次不复活，新安装 ID 下没有旧数据。 |
| 同一天同账号使用两个版本，再切换另外两个账号 | 两个版本都有登记，同一账号只占一个每日名额。 |
| 九个仍有效的日期版本组合或接近正文上限的数据 | 分成多个合法批次，未取走的计数保留，总计数不增加也不丢失。 |

聚焦入口在该模块建立后使用：

```bash
cargo test --locked -p ubaa-core --features test-contract app_service
```

完成判据：状态、队列和删除标记在跨连接与重启后保持合同语义，测试证明被禁止的动作没有写库或发送请求。

## 步骤三：实现 Worker 上报、删除和 Core 上传

产物：客户端到本地 Worker/D1 的完整上报与删除链路。

- [ ] 建立 D1 初始迁移，包含合同第 11 节全部明细、批次、墓碑和聚合表；按真实删除与日期查询建立必要索引。测试直接执行迁移文件。
- [ ] 实现请求校验、128 KiB 正文限制、日期接收窗口、HMAC 转换和白名单落库。Worker 不输出请求正文或派生标识，关闭 Workers Logs 与 Logpush，不增加 CORS 支持。
- [ ] 按合同第 11.1 节在单个 D1 batch 中去重：以 `INSERT OR IGNORE` 写入带本次请求 `nonce` 的批次行，每条明细 upsert 以该 `nonce` 存在为条件，所有写入带墓碑条件。不在 batch 之外先查询再决定是否写入。已存在的批次返回 204 且不重复累加；其他数据库错误不能被当成重复批次吞掉。测试顺序重发和同一 `batch_id` 的并发提交，两者的计数都只累加一次。
- [ ] 删除在同一个 D1 batch 中写入墓碑并清除旧安装 ID 的全部明细。测试先上传后删除、先删除后上传，以及预查完成后才发生删除的交错，保证数据库最终没有旧 ID 明细。
- [ ] 配置合同规定的三组 Rate Limiting 绑定，验证命中后返回 429。按照官方的节点近似计数语义实现，不增加全局计数服务。
- [ ] 为 Core 创建独立 transport，复用 HTTP 抽象而不复用学校 Cookie 容器或路线客户端。测试 TLS 配置、请求头、目标主机和跨主机重定向限制。只有非 Release 构建可以访问本机回环地址，回环地址允许 HTTP；Release 构建拒绝 HTTP，任何构建都不放宽证书校验。
- [ ] 实现响应处理：204/410 移除批次，400/413 移除并写安全诊断，429/5xx/网络失败保留原批次。测试服务端已提交但客户端响应丢失后的重发，数据库计数保持一次。
- [ ] 实现删除协调：先持久化标记再发送，204 后同一事务清旧数据、换安装 ID、清标记，失败保留。重试时机按合同第 6.1 节：
  - GUI 按自身触发时机在任何同意状态下重试，非 `agreed` 状态下只发删除请求，设置页可以手动重试；
  - `agreed` 状态下，命令模式在上传时机先重试删除；
  - 命令模式在非 `agreed` 状态下不发任何应用服务请求。

  测试 `basic` 状态下删除失败后重启 GUI，并同时运行命令模式。
- [ ] 将 Rust 实际序列化结果交给 Worker 校验和处理，验证请求与响应的双向兼容。联调用真实 HTTP 边界和本地 D1 查询核对结果。

完成判据：有效批次写入一次，重试不重复，删除成功后旧 ID 无明细，删除结果未知可重启恢复。网络失败不改变业务结果。

## 步骤四：完成 GUI、命令模式与全部事件接线

产物：用户可以查看政策、同意、关闭统计、撤回同意和删除数据，GUI 与命令模式共享同一规则。

- [ ] 增加 facade 和 typed Bridge 操作：读取应用服务状态、提交同意选择、设置遥测开关、入队事件、触发上传、发起删除、读取删除结果。返回值包含真实可用性和持久化状态，界面不得先假定操作成功。
- [ ] 生成 FRB 绑定并更新 Dart 消费者和版本声明。手写 API、机械生成物与业务接线按可审查主题提交，生成文件只由项目工具生成。
- [ ] 接入 `TelemetryClient` 和 `TelemetryPolicy`。当前 `controller/session/settings.dart` 关闭统计时调用 flush，改成 Core 的关闭并清空操作；当前 `controller/lifecycle/diagnostics.dart` 使用 `source` 表达耗时桶，改为合同的 `timings` 维度。
- [ ] 接齐合同事件、错误类别、耗时和安全源码位置。捕获边界只提取白名单值，原始异常、完整堆栈、URL、诊断报告不进入队列。测试遥测自身失败不会再生成遥测形成递归。灾难性进程终止不能保证上报，按实际捕获能力记录覆盖范围。
- [ ] 实现 `crash` 事件的两个来源：
  - Dart 侧接入 `FlutterError.onError` 和 `PlatformDispatcher.instance.onError`，保留现有处理链，只提取异常类型名（去掉泛型参数）和至多一项 `package:ubaa_*` 源码位置；
  - Rust 侧先核实 FRB 现有的 panic 处理方式，再在 Bridge 安装 panic 钩子，`error_code` 固定为 `panic`，只取 `crates/ubaa_*` 内的位置，不读取 panic 消息。

  测试原有错误处理仍然执行、消息和堆栈不进入队列。
- [ ] 按合同第 3.1 节建立隐私政策的唯一来源：
  - 在 `docs/site/tech/privacy-policy.md` 的 frontmatter 加入 `policy_version` 和 `policy_body_sha256`；
  - 构建时由项目脚本把正文和版本生成到应用内，GUI 和命令模式使用同一个生成值，宿主初始化时传给 Core；
  - 新增检查：正文摘要与登记值不符、应用内生成物与来源不一致时失败，并补充对应的失败反例，接入按改动检查；

## 步骤六：实现统计汇总、清理和发布工具

产物：可重复执行的汇总清理任务、可检查的公告渠道内容和明确区分本地校验与远端写入的命令。

- [ ] 实现独立的定时处理函数，测试可传入确定日期。重算 `[D−8,D+1]` 十个校园日及相交月份，覆盖式更新聚合结果，重复执行不能再次累加。重算后没有明细的旧分组必须消失或归零，避免删除后仍保留旧聚合值。
- [ ] 按 `all`、平台、渠道、版本和年级分别计算用户与设备去重；匿名设备不计入用户数。汇总成功后才按保留期清理明细、批次和墓碑，任一必要汇总失败时不清除其依赖的明细。
- [ ] 三步全部成功后在 `job_state` 记录本次 D 作为 L。若 L 早于 D − 1，重算起点提前到 L − 7，月份范围相应扩大，起点不早于明细保留期；任一步失败时不更新 L。
- [ ] 覆盖第七天晚间数据、上月最后一天迟到数据、每月八日定稿、未定稿设备删除、多平台同用户、重复运行、漏跑一天和首次运行。已定稿结果按合同保留。
- [ ] 配置校园时间每日 03:00 的 Cron。Workers Cron 使用 UTC，因此表达式为 `0 19 * * *`。处理函数用触发器的计划时间按 Asia/Shanghai 换算 D，不读取运行时的当前时间。依据见 [Cloudflare Cron 文档](https://developers.cloudflare.com/workers/configuration/cron-triggers/)。

- [ ] 给发布脚本增加假 CLI 测试，证明内容校验失败、目标缺失或凭据缺失时没有远端写入。部署手册写明账号、Worker、D1/KV 绑定、域名、Secret、迁移顺序、查询和回退方法。密钥只从本机环境或对应 Secret 注入，测试使用合成值。

完成判据：全部汇总边界结果正确，清理不会先删后算，漏跑后的补算覆盖迟到数据，网站公告列表与 App 使用同一来源，发布无效内容不会产生远端写入，命令副作用已登记到开发命令和脚本说明。

## 外部条件与完成判定

| 项目 | 无人值守处理 | 对完成结论的影响 |
| --- | --- | --- |
| 本地实现、必需确定性检查或端到端测试失败 | 定位并修复；缺工具按项目入口准备；无可行替代时保留具体失败和恢复方法。 | 工程实现未完成，不得标记通过。 |
| Cloudflare 账号、资源目标、自定义域名或密钥未配置，或缺少部署授权 | 完成部署工具、离线校验、本地 D1/KV 验收和手册，继续工程工作。 | 可以判断工程完成；生产部署仍为未执行。 |
| 有明确部署目标及当前会话授权 | 使用显式部署发布入口，先迁移/部署服务再发布支持该合同的客户端；用合成数据检查 bootstrap、上报、去重、删除和定时任务，记录 D1 实际位置。 | 只有实际部署及对应验收通过，才能标记生产部署完成。 |
| 缺少 Windows/Linux/OHOS 环境或目标设备 | 完成本机及可用环境的检查，记录具体平台、缺少条件和重跑命令；不擅自使用其他聊天的工作树。 | 对应平台验收未完成，不能宣称六平台发布就绪。 |
| 远端 CI 未运行 | 保留本地候选和验证结果，按后续推送授权运行同一候选 CI。 | 远端 CI 状态为未验证。 |
| 学校真实协议验证、商店审核或真实用户数据测试 | 遵循项目当前授权和发布要求；工程测试使用合成账号及可注入 transport。 | 单独记录，工程结果不替代真实协议、商店或发布验收。 |

工程完成同时要求：合同全部功能有生产接线；合同指定场景和必需检查通过；部署发布工具可按手册运行；没有隐藏的功能占位或被忽略的失败；本地提交与状态记录完整。生产部署、平台发布和商店上架有各自证据后分别更新结论。

交付说明只列实际实现、验证结果、候选提交、运行入口以及尚缺的外部条件。执行中发生的临时错误和已放弃方案不进入长期产品文档。
